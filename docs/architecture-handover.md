# Architecture Handover

> **Draft** (t-handover-docs-draft). Written from the code as built on `main`, before the production cutover. It will be finalised once the site is live (spec §10, `t-owner-handover-finish`). Only three things still wait for the cutover: the live URL, the revision names, and the actual Graph token mint dates. They are marked TODO.

## In one paragraph

A small group-trip journal. Riders use it to log stops (a place, time, notes and photos) from their phones, often with no signal. Friends follow along on a map. The whole thing is **one Docker container**: a Python FastAPI server that answers `/api/*` and also serves the built web app. Stop, bike and trip data lives in **Postgres**. Photos live in **S3-compatible object storage**. A separate job copies photos to **OneDrive** as an archive. Nothing ever reads from OneDrive. The diagram is in [architecture-diagram.md](architecture-diagram.md).

## The pieces

| Piece | Local | Production | Code that touches it |
|---|---|---|---|
| Database | `docker-compose` service `postgres` | Neon | `backend/app/data/` only |
| Photo storage | `docker-compose` service `minio` | Cloudflare R2 | `backend/app/storage/s3_client.py` only |
| Archive | — | OneDrive via Microsoft Graph | `backend/app/storage/onedrive_sync.py` (off-limits without approval) |
| Host | `docker compose up` | Azure Container Apps: one Container App (the web app and API) plus one scheduled Container Apps Job (the OneDrive sync). Both run the same image from GitHub Container Registry (GHCR) | `Dockerfile`, `infra/azure/README.md` |

The code has no "if Neon / if MinIO" branches. The provider is chosen by configuration (`DATABASE_URL`, `S3_ENDPOINT_URL`, …; see `backend/app/core/config.py`). Routes never import a cloud SDK directly. They go through `data/` and `storage/`, which keeps a provider swap contained to those two folders.

OneDrive sync runs as its own command, `python -m app.storage.onedrive_sync`, and nothing calls it during a request. In production it is a **scheduled Container Apps Job**: every 30 minutes (cron `*/30 * * * *`, evaluated in UTC), from the same GHCR image as the app with only the command changed, one run at a time. Each run archives whatever is still pending and exits. The job is defined in `infra/azure/README.md` ("OneDrive sync job") and is created at cutover. If it is not running, nothing breaks for users: photos are served from object storage, and the next successful run catches up.

## Generated API client

The frontend never hand-writes a fetch call. The flow is:

1. The FastAPI models and routes (every field and route has a `description=`) produce the OpenAPI document.
2. A snapshot of it is committed at `frontend/openapi.json`.
3. Kubb reads the snapshot and generates types, clients and TanStack Query hooks into `frontend/src/api/gen/`.
4. The generated code calls `frontend/src/api/client.ts`. That client sets the JSON content type (never for FormData) and throws an `ApiError` carrying the parsed error envelope, or no envelope when the server didn't answer. The offline queue relies on that difference.

Regenerate after any backend contract change:

```
cd backend && uv run python -c "import json,pathlib; from app.main import app; pathlib.Path('../frontend/openapi.json').write_text(json.dumps(app.openapi(), indent=2)+'\n', encoding='utf-8', newline='\n')"
cd frontend && npm run generate:api
```

## Access model

There are no accounts. Each trip row has two random slugs. The **rider slug** can read and write. The **viewer slug** can only read. `core/security.py` enforces this:

- An unknown slug gets `404`, always.
- A viewer slug on a write gets `403`.
- The two responses are kept distinct on purpose. A `403` must never confirm that a guessed slug exists, and a viewer must not be told a working link is broken.

`TripOut.access` tells the UI whether to show write controls. It only affects what is shown. The server check is the real enforcement.

A **leaked rider link** is handled by rotating `rider_slug` with one SQL `UPDATE` in Neon (decision-log Entry 21). There is deliberately no PIN. `FORBIDDEN` is a never-retry error, so a PIN would permanently fail queued stops. After rotation, every rider needs the new link. Any stops still queued under the old slug will fail with `NOT_FOUND`. The drill is in [real-device-test-plan.md](real-device-test-plan.md).

## Offline design

- **Write queue** (`frontend/src/offline/queue.ts`, decision-log Entry 19). There is one IndexedDB store. A stop and its photos are written in one transaction, stop first, so sending in order (FIFO) keeps a photo behind its stop. The queue is sent from the page, never from service-worker Background Sync, which iOS lacks. Sending starts on app start, when the app becomes visible, on the `online` event, and on a backoff timer (5s doubling to a 5min cap). A send attempt is the only connectivity test; `navigator.onLine` is not trusted.
- **Several tabs, one queue.** Where the browser has the Web Locks API, only the tab holding the `btj-queue-drain` lock sends, so two tabs never send the same entry. Where it has `BroadcastChannel`, every queue change is announced on `btj-queue`, so other tabs' notices refresh. Without either, each tab falls back to its own in-memory guard. Each send has a timeout (30s for a stop, 120s for a photo), so a request that never answers cannot hold the lock; a timeout is retried like a network failure. The automated queue suites exercise only the no-lock fallback (`t-queue-lock-path-coverage`).
- **Retry rules** (the Error envelope section of api-contract.md). `VALIDATION_ERROR`, `METHOD_NOT_ALLOWED`, `CONFLICT`, `FORBIDDEN` and `NOT_FOUND` are never retried. The entry is marked failed and kept until the rider dismisses it, and a failed stop fails its queued photos with it. Any other failure, including no response, counts an attempt and is retried. `QueueNotice` shows "still trying" once an entry reaches 10 attempts.
- **Idempotency.** Every stop, photo and bike id is a client-generated UUID fixed before the first send. A replay returns `200` with no duplicate. The same id under a different trip returns `409` (Entry 14).
- **Photos** (Entry 20). The phone resizes each photo to a ~1600px JPEG, well under 1 MiB, and uploads it as **one** request. Resuming happens in the queue: the bytes stay in IndexedDB until a `2xx`. S3 multipart was rejected because parts must be at least 5 MiB, so a photo this small is a single part with nothing to resume.
- **App shell.** A Workbox service worker serves the app offline (`/api` is excluded). The last `TripOut` is saved per slug and used as `initialData`, so a cold open offline shows the trip. Stops, the map and photos are not saved, so they need the network. Bike edits are online-only direct mutations and are not queued.
- **Location.** Add stop asks for GPS only for a rider; a viewer is never asked (the viewer is redirected before the request). If GPS is denied, fails, or gives no answer within 15 seconds (the app's own timer, so a permission prompt left unanswered also falls back), the rider taps the map instead and the stop is marked "approximate location".
- **Times** (Entry 26). Stored as instants (UTC). Shown in the reader's own time zone, with the zone named, so a friend at home and a rider on the road never confuse the two. The rider's own offset is not stored.
- **After a deploy.** An open page may ask for a code chunk the new build removed. `staleChunk.ts` catches that and reloads once onto the new build (at most once per 30 seconds, so it cannot loop).
- **Expired photo links.** Photo URLs are valid for an hour. If one fails to load, the stop page fetches fresh URLs once.
- **iOS storage isolation** (Entry 18). The installed app and Safari have separate storage, so riders must capture from the installed app. `/` redirects to the last slug, or shows "Paste your trip link" on first launch.

## Deploy and operations

The step-by-step commands are in [deploy-cutover-runbook.md](deploy-cutover-runbook.md). This section explains how production fits together and what to do when. The devops agent's version is `.claude/skills/deploy/SKILL.md`.

### What runs where

| Thing | Where | Notes |
|---|---|---|
| Web app + API | One Azure Container App, free tier | External HTTPS ingress to port 8000, plain HTTP refused. Scales to zero when idle, so the first request after a quiet spell waits a few seconds (the app shows "waking up"). **Multiple-revision mode**, so a rollback is a traffic switch |
| OneDrive sync | One Azure Container Apps Job | Same image, command overridden. Cron `*/30 * * * *` in UTC. One run at a time: 900s timeout, no retries, so a run always ends before the next starts |
| Image | GitHub Container Registry (GHCR) | Tagged with the 12-character commit hash. Never `latest`, never a reused tag, because rollback depends on each revision naming a distinct image |
| Database | Neon | Migrations are forward-only and run by you, from your shell |
| Photos | Cloudflare R2 | The source of truth for photos. No CORS needed: browsers never upload to R2 directly |
| Archive | Your OneDrive, via Microsoft Graph | Write-only. Nothing reads it |

### Secrets

The names are listed in runbook §2 and match `.env.example`. Values live only in your password manager and in Azure's secret stores. **The app and the Job have separate secret stores**: every secret is set on both, under the same names, and changed on both together. `S3_PUBLIC_ENDPOINT_URL` stays unset in production, because R2's address works for the browser too.

### The Graph refresh token (decision-log Entry 22)

The sync uses one refresh token for the whole trip. It lasts about **90 days from when you mint it** (Microsoft gives no exact figure for personal accounts).
- **Mint it close to departure** with the helper (`uv run python -m app.storage.get_refresh_token`), in your own terminal, never in an agent session.
- Record the **mint date** and the **client secret's expiry date** next to the secrets. Check that both fall after the trip ends.
- It can also die early if you revoke sessions, remove the app's consent, or reset your password.
- If archiving stops, nothing is lost: re-mint, update `GRAPH_REFRESH_TOKEN` on the app **and** the Job, and the next run catches up (runbook §5, "If archiving stops mid-trip").

### A normal deploy

1. Build from a clean, committed tree and push to GHCR, tagged with the commit hash.
2. Note which revision is serving now. That is the rollback target.
3. **Migrate Neon before moving any traffic.** The old revision keeps serving during this, so a migration must also work with the previous image.
4. Update the Container App to the new tag. This creates a revision named `<app>--rel-<tag>`.
5. When the new revision reports `Healthy`, move 100% of traffic to it.
6. Update the Job to the **same tag**, so the archive never runs different code from the app.
7. Check `/api/health` and that the site loads.

### Rollback

Send traffic back to the previous revision (runbook §8). Don't rebuild forward under pressure. A rollback does not undo a migration, so check that the older image works with the current schema. A **leaked rider link** is not a rollback: rotate `trips.rider_slug` with one SQL `UPDATE` in Neon (decision-log Entry 21) and share the new link.

### Health

`/api/health` answers `200` when the process is up. It does not check the database or storage. Locally, the Dockerfile `HEALTHCHECK` and compose use it. Container Apps ignores `HEALTHCHECK`, so production needs its own liveness probe in the app definition (`t-infra-container-apps-probe`).

### Logs

Container Apps sends stdout to Log Analytics. The production image starts uvicorn with a logging config that removes the trip slug from logged URLs (`backend/log_config/`), because the slug is the access credential. The `--reload` dev command does not use it, which is fine locally.
