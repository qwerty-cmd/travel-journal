# Architecture Handover

> **Draft** (t-handover-docs-draft). Written from the code as built on branch `chore/m1-m2-review-fixes`, before the production cutover. It will be finalised once the site is live (spec §10). Sections marked TODO depend on that cutover.

## In one paragraph

A small group-trip journal. Riders use it to log stops (a place, time, notes and photos) from their phones, often with no signal. Friends follow along on a map. The whole thing is **one Docker container**: a Python FastAPI server that answers `/api/*` and also serves the built web app. Stop, bike and trip data lives in **Postgres**. Photos live in **S3-compatible object storage**. A separate job copies photos to **OneDrive** as an archive. Nothing ever reads from OneDrive. The diagram is in [architecture-diagram.md](architecture-diagram.md).

## The pieces

| Piece | Local | Production | Code that touches it |
|---|---|---|---|
| Database | `docker-compose` service `postgres` | Neon | `backend/app/data/` only |
| Photo storage | `docker-compose` service `minio` | Cloudflare R2 | `backend/app/storage/s3_client.py` only |
| Archive | — | OneDrive via Microsoft Graph | `backend/app/storage/onedrive_sync.py` (off-limits without approval) |
| Host | `docker compose up` | Azure Container Apps (TODO) | `Dockerfile`, `infra/` |

The code has no "if Neon / if MinIO" branches. The provider is chosen by configuration (`DATABASE_URL`, `S3_ENDPOINT_URL`, …; see `backend/app/core/config.py`). Routes never import a cloud SDK directly. They go through `data/` and `storage/`, which keeps a provider swap contained to those two folders.

OneDrive sync runs as its own command, `python -m app.storage.onedrive_sync`, and nothing calls it during a request. **Drift to know about:** the diagram shows it as "timer-triggered", but **nothing schedules it yet**. Before go-live someone must scope and approve a scheduler, probably a Container Apps Job. See the §0 blockers in [deploy-cutover-runbook.md](deploy-cutover-runbook.md).

## Generated API client

The frontend never hand-writes a fetch call. The flow is:

1. The FastAPI models and routes (every field and route has a `description=`) produce the OpenAPI document.
2. A snapshot of it is committed at `frontend/openapi.json`.
3. Kubb reads the snapshot and generates types, clients and TanStack Query hooks into `frontend/src/api/gen/`.
4. The generated code calls `frontend/src/api/client.ts`. That client sets the JSON content type (never for FormData) and throws an `ApiError` carrying the parsed error envelope, or no envelope when the server didn't answer. The offline queue relies on that difference.

Regenerate after any backend contract change:

```
cd backend && uv run python -c "import json,pathlib; from app.main import app; pathlib.Path('../frontend/openapi.json').write_text(json.dumps(app.openapi(), indent=2)+'\n', encoding='utf-8', newline='\n')"
cd frontend && npm run generate:api
```

## Access model

There are no accounts. Each trip row has two random slugs. The **rider slug** can read and write. The **viewer slug** can only read. `core/security.py` enforces this:

- An unknown slug gets `404`, always.
- A viewer slug on a write gets `403`.
- The two responses are kept distinct on purpose. A `403` must never confirm that a guessed slug exists, and a viewer must not be told a working link is broken.

`TripOut.access` tells the UI whether to show write controls. It only affects what is shown. The server check is the real enforcement.

A **leaked rider link** is handled by rotating `rider_slug` with one SQL `UPDATE` in Neon (decision-log Entry 21). There is deliberately no PIN. `FORBIDDEN` is a never-retry error, so a PIN would permanently fail queued stops. After rotation, every rider needs the new link. Any stops still queued under the old slug will fail with `NOT_FOUND`. The drill is in [real-device-test-plan.md](real-device-test-plan.md).

## Offline design

- **Write queue** (`frontend/src/offline/queue.ts`, decision-log Entry 19). There is one IndexedDB store. A stop and its photos are written in one transaction, stop first, so sending in order (FIFO) keeps a photo behind its stop. The queue is sent from the page, never from service-worker Background Sync, which iOS lacks. Sending starts on app start, when the app becomes visible, on the `online` event, and on a backoff timer (5s doubling to a 5min cap). A send attempt is the only connectivity test; `navigator.onLine` is not trusted.
- **Retry rules** (the Error envelope section of api-contract.md). `VALIDATION_ERROR`, `METHOD_NOT_ALLOWED`, `CONFLICT`, `FORBIDDEN` and `NOT_FOUND` are never retried. The entry is marked failed and kept until the rider dismisses it, and a failed stop fails its queued photos with it. Any other failure, including no response, counts an attempt and is retried. `QueueNotice` shows "still trying" once an entry reaches 10 attempts.
- **Idempotency.** Every stop, photo and bike id is a client-generated UUID fixed before the first send. A replay returns `200` with no duplicate. The same id under a different trip returns `409` (Entry 14).
- **Photos** (Entry 20). The phone resizes each photo to a ~1600px JPEG, well under 1 MiB, and uploads it as **one** request. Resuming happens in the queue: the bytes stay in IndexedDB until a `2xx`. S3 multipart was rejected because parts must be at least 5 MiB, so a photo this small is a single part with nothing to resume.
- **App shell.** A Workbox service worker serves the app offline (`/api` is excluded). The last `TripOut` is saved per slug and used as `initialData`, so a cold open offline shows the trip. Stops, the map and photos are not saved, so they need the network. Bike edits are online-only direct mutations and are not queued.
- **iOS storage isolation** (Entry 18). The installed app and Safari have separate storage, so riders must capture from the installed app. `/` redirects to the last slug, or shows "Paste your trip link" on first launch.

## Testing

- **Backend:** `cd backend && uv run pytest`. The tests run against the real docker-compose Postgres and MinIO, so start `docker compose up postgres minio` first. Access control, data integrity and the error envelope get the most rigour.
- **Frontend:** `cd frontend && npm test`. This runs Vitest with jsdom and `fake-indexeddb`. The queue tests simulate network loss and a restart.
- **Real devices:** see [real-device-test-plan.md](real-device-test-plan.md). This covers what jsdom can't: iOS install, GPS, HEIC photos, and offline cold open.

## Open debt worth knowing

These are triggered items: not started, and waiting for a specific event. Each one's trigger is in progress-notes.md.

- `t-api-healthcheck-wiring`: `/api/health` exists, but no container or compose healthcheck uses it.
- `t-access-log-slug-exposure`: the uvicorn access log records slugs from URLs.
- `t-dockerignore-route-tree`: a host-generated `routeTree.gen.ts` can leak into the image build.
- `t-onedrive-preflight-check` (human step): a real Graph sync against the live tenant. Not yet verified that Graph accepts the request shape.
- `t-onedrive-per-photo-isolation`: an S3 or JSON failure aborts the whole sync run instead of skipping that photo.
- `t-onedrive-filename-url-encoding`: `#` or `?` in an id breaks the Graph upload URL.
- `t-mark-archived-overwrite-guard`: `mark_archived` can overwrite an existing OneDrive id. This matters once runs overlap.
- `t-photo-upload-stream-to-s3`: an upload is read fully into memory before it goes to S3.
- `t-photo-insert-echoes-argument`: a `201` photo response echoes the device offset, while replays return UTC. Awaiting a gate ruling.
- `t-bare-409-envelope-bypass`: a bare `HTTPException(409)` skips `ApiError.conflict`.
- `t-schema-type-drift-check`, `t-bike-order-collation`, `t-head-route-kwarg-divergence`: test-strength gaps.
- `t-qa-mutation-hook`: agent tooling. Nothing enforces the qa scratch-tree rule.
- Not yet filed as a task: the Neon `sslmode` handling in `normalize_database_url` (runbook §0; recorded under `s-cloud-service-setup`).
